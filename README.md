# «Защищённый смартфон» — предсказание отклика на страховое предложение

RuCode 2026 AI · Сбер · задача B (BASE)

**Задача.** Бинарная классификация: по профилю клиента предсказать, купит ли он
страховку «Защищённый смартфон» (`accepted` ∈ {0, 1}). Метрика — **F1**.

**Итог.** Финальная модель — логистическая регрессия на B-сплайнах, **167 параметров**.

| Оценка | F1 | AUC |
|---|---|---|
| OOF (5×5, порог по тому же OOF — слегка оптимистично) | 0.9622 | 0.99369 |
| **Nested CV (5×4, 20 фолдов, честная)** | **0.9595 ± 0.0016** | **0.99367 ± 0.00053** |

OOF-строка зависит от seed (разные разбиения CV): при seed 136923631 было
0.9616 / 0.99368, при seed 14310590 — 0.9622 / 0.99369. Nested CV от seed
обучения не зависит, поэтому именно она — рабочая оценка.

## Быстрый старт

```bash
pip install -r requirements.txt

python eda.py          # разведочный анализ -> reports/eda_summary.txt + eda/*.png
python train.py        # обучение (seed выбирается случайно) -> models/
python predict.py      # предсказание БЕЗ обучения -> submission_seed_{SEED}.csv
python verify.py       # самопроверка: веса, детерминированность, формат ответа
python evaluate.py --compare-candidates   # честный nested-CV выбор модели
```

`train.py --seed 42` фиксирует seed вручную. Seed сохраняется в `models/meta.json`
и попадает в имя файла ответа, как требует регламент.

## Разведочный анализ (ключевые находки)

Полный отчёт — `reports/eda_summary.txt`, графики — `eda/`.

**1. Состав.** 6000 строк train / 1000 строк public_test, 28 признаков,
доля класса 1 = 0.3285. Дубликатов и утечек по `customer_id` нет.

**2. Пропуски делятся на два принципиально разных типа.**

*Структурные* — пропуск полностью определён другим столбцом, новой информации
не несёт (проверено на всех 6000 строк):

```
loan_amount      == NaN  <=>  has_credit == 0          (100% совпадение)
insurance_claims == NaN  <=>  previous_insurance == 0  (100% совпадение)
```

*Неструктурные (MNAR)* — пропуск сам по себе является признаком:

| признак | P(accepted), значение есть | P(accepted), пропуск | доля пропусков |
|---|---|---|---|
| `credit_score` | 0.3399 | **0.1988** | 8.0% |
| `mobile_app_usage` | 0.3318 | **0.2075** | 2.6% |

Поэтому в признаки добавлены индикаторы `credit_score_isna`, `mobile_app_usage_isna`,
а сами пропуски **не заполняются** — бустинг обрабатывает NaN нативно.
Индикаторы для `loan_amount` / `insurance_claims` добавлять бессмысленно —
это точные копии уже имеющихся флагов.

**3. Редкие и невидимые категории.** В train есть `family_status='widowed'`
(1 строка) и `employment_type='student'` (2 строки); в public_test есть
`employment_type='retired'`, которого в train **нет вообще**. Отсюда требование:
фиксированный словарь категорий + бакет `UNSEEN` и корректная обработка
невидимых значений на инференсе (см. «Проверенные гипотезы», п. 7).

**4. Ковариатного сдвига нет.** KS-тест по всем числовым признакам train vs test
даёт p > 0.05, максимальное расхождение долей категорий — 0.02. Значит,
настройки порога, подобранные на train, переносимы на тест.

**5. Сигналы очень сильные и почти монотонные.** Доля покупок по бинам:

```
number_of_card_transactions_month:  0.004 (при 2-8) -> 1.000 (при >= 56)
marketing_contacts_last_year:       0.115 (при 0-1) -> 1.000 (при >= 10)
number_of_bank_products:            0.147 (при 1-2) -> 0.938 (при 8)
smartphone_brand:  Apple 0.810 | Google 0.522 | Samsung 0.455 | Other 0.021
region:            Москва 0.578 против 0.270 в среднем по остальным 11
employment_type:   unemployed 0.035 против self_employed 0.404
```

Топ-5 числовых признаков по Спирмену: `smartphone_price` 0.693,
`monthly_income` 0.652, `number_of_card_transactions_month` 0.599,
`credit_score` 0.519, `average_monthly_balance` 0.518.

**6. Мультиколлинеарность умеренная** (до r = 0.763 между `monthly_income` и
`number_of_card_transactions_month`) — данные сгенерированы из общих латентных
факторов. Для деревьев это не мешает, для линейной модели закрыто L2.

**Главный вывод EDA, определивший решение.** Зависимость вероятности покупки от
каждого числового признака **гладкая и монотонная, но не линейная**. Это значит,
что нужна модель, способная представить гладкую нелинейность, — и не обязательно
дерево.

## Решение

### Модель

```
33 числовых признака ──► SplineTransformer(n_knots=3, degree=3, include_bias=False)
                              └──► 132 базисные колонки
34 one-hot колонки категорий ──► passthrough
                              └──► 166 колонок ──► StandardScaler
                                                └──► LogisticRegression(L2, C=0.3)
```

**167 параметров** (166 весов + intercept), вес файла — 26 КБ.

### Почему именно так

EDA показал, что зависимость гладкая и монотонная. Бустинг аппроксимирует её
ступеньками, и на 6000 строк с сильным шумом в метках эти ступеньки начинают
подгонять шум. Сплайны дают линейной модели ровно нужную гладкую нелинейность,
и переобучаться ей нечем — параметров в 50 раз меньше, чем у одного LightGBM.

Это подтверждается двумя независимыми переборами, в обоих выигрывает **более
сильная регуляризация**:

*LightGBM, 40 конфигураций* (`explore/sweep_lgb.py`, `explore/sweep2.py`):

| конфигурация | OOF AUC |
|---|---|
| `num_leaves=31`, без регуляризации (стандартный дефолт) | 0.99209 |
| `num_leaves=7`, `reg_alpha=2`, `reg_lambda=20` | **0.99302** |

*Сплайновая логистика, 48 конфигураций* (`explore/spline_sweep.py`), меньше
узлов — лучше:

| n_knots | OOF AUC |
|---|---|
| 6 | 0.99305 |
| 4 | 0.99342 |
| **3** | **0.99375** |

### Порог

Порог подбирается на OOF-предсказаниях перебором всех кандидатов за O(n log n).
Для F1 optimum достигается при правиле «предсказывать 1, если p > F1\*/2»
(вывод: добавление объекта с вероятностью p в множество S повышает
E[F1] = 2·Σp /( |S| + P_total ) тогда и только тогда, когда p > F1/2).
При ожидаемом F1 ≈ 0.96 это даёт порог ≈ 0.48 — близко к 0.5, что и наблюдается.

Фактически выбирается число объектов k, при котором F1 максимальна; реализация
через среднее нормированных рангов дополнительно фиксирует предсказанную долю
единиц на уровне обучающей, что устойчиво при отсутствии сдвига (п. 4 EDA).

### Воспроизводимость

Задача выпуклая, поэтому обученные веса **не зависят от `random_state` вообще**
(проверено `verify.py`: повторное обучение даёт max|diff| = 0.00e+00).
Seed влияет только на разбиение CV и, через него, на четвёртый знак порога.
Все генераторы фиксируются в `train.py:set_global_seed`.

## Честная оценка (почему именно nested CV)

Подбор порога по тем же OOF-предсказаниям, на которых считается F1, даёт
оптимистичное смещение. В этом решении оно измерено и составляет ~0.005:

| оценка | F1 |
|---|---|
| OOF, порог по тому же OOF | 0.9622 |
| nested CV (порог и модель не видят тестовую фолду) | 0.9595 ± 0.0016 |

`evaluate.py` реализует nested CV: внутри каждой внешней фолды отдельный
внутренний 4-fold подбирает порог, и только потом он применяется к отложенной
части. Протокол — `reports/nested_cv.log`.

Два момента, за которыми в обвязке следят отдельно, потому что именно они
незаметно завышают оценку:

* ранги нормализуются **по пулу** всего внутреннего OOF, а не внутри каждой
  фолды, — иначе сравнивались бы ранги из разных фолдов, чего на инференсе нет;
* медианы для заполнения пропусков считаются внутри тренировочной части каждой
  фолды (`nested_cv(..., df=df)`), как это делает `predict.py` по `meta.json`.

## Проверенные гипотезы

1. **Инженерные признаки.** `log1p` для 5 тяжелохвостых признаков, индикаторы
   MNAR-пропусков, отношения (`доход/цена телефона`, `долг/доход`,
   `остаток/доход`, `остаточная стоимость телефона`), произведения
   (`транзакции × доля онлайн`). Для линейной модели логарифмы дали
   +0.0008 AUC; бустингу инженерные признаки **не дали ничего** (0.9922 → 0.9922),
   деревья сами находят пороги. Оставлены только те, что не ухудшают.

2. **Семейства моделей** (`explore/screen3.py`, `explore/zoo.py`, OOF AUC):
   логистическая регрессия 0.9922, LightGBM 0.9921, XGBoost 0.9923,
   CatBoost 0.9922, MLP(128-64-32) 0.9912, ExtraTrees 0.9856, RandomForest 0.9837.
   Случайные леса заметно хуже — им не хватает гладкости.

3. **Сильная регуляризация деревьев** — главный источник прироста внутри
   бустинга: +0.001 AUC (см. таблицы выше).

4. **Сплайны для линейной модели** — главный источник прироста в решении
   в целом: 0.99223 → 0.99379 AUC.

5. **Ансамблирование** (среднее нормированных рангов). Даёт большой выигрыш
   над одиночным бустингом (0.99260 → 0.99345), потому что логистическая
   регрессия скоррелирована с LightGBM всего на 0.965, тогда как
   XGBoost/CatBoost — на 0.98–0.998. Но сплайновая логистика **в одиночку
   обгоняет любой собранный ансамбль** (таблица ниже), поэтому финальная
   модель состоит из одной модели.

6. **XGBoost исключён** по двум причинам. (а) Он дублирует LightGBM:
   ранговая корреляция предсказаний 0.9975, добавка к ансамблю нулевая.
   (б) Он единственный из движков падает с `Found a category not in the
   training set`, если в тесте встречается код категории больше максимального
   из обучающих. На наших данных это не теория: `family_status='widowed'`
   встречается в train ровно 1 раз (в CV-фолду он может не попасть), а
   `employment_type='retired'` в train отсутствует вовсе, но есть в
   public_test. LightGBM, CatBoost и логистическая регрессия такой случай
   обрабатывают корректно — воспроизводимая проверка в `explore/unseen_test2.py`.
   `predict.py` дополнительно печатает предупреждение о невидимых категориях.

7. **Предел достижимого.** Изотоническая калибровка OOF-предсказаний бустинга
   показала, что модель уже выбирает почти весь доступный F1 при своём
   ранжировании (потолок 0.9534 против фактических 0.9532), то есть улучшать
   нужно было **ранжирование**, а не порог. Сплайны сдвинули именно его:
   0.9926 → 0.9937 AUC.

8. **Калибровка.** Бустинг переусердствовал с уверенностью на обоих хвостах
   (в бакете p∈[0.95, 0.999] фактическая доля 0.936 против предсказанной 0.987),
   а в средней зоне недооценивал (0.31 против 0.24). Ошибки распределены
   пропорционально по всем категориям и регионам — систематической группы,
   которую модель «не понимает», нет; остаток — необратимый шум Бернулли.

9. **Баланс и порог.** Доля единиц в ответе на public_test — 0.3310 против
   0.3285 в train, что согласуется с отсутствием сдвига.

### Протокол выбора модели (nested CV 5×2, `reports/nested_cv.log`)

| состав | nested F1 | nested AUC | ~параметров |
|---|---|---|---|
| lgbm (тюнингованный) | 0.9473 | 0.99260 | 8 400 |
| logreg (без сплайнов) | 0.9474 | 0.99235 | 140 |
| lgbm + catboost | 0.9511 | 0.99284 | 17 000 |
| lgbm + logreg | 0.9531 | 0.99345 | 8 500 |
| lgbm + catboost + logreg | 0.9559 | 0.99350 | 17 000 |
| lgbm + lr_spline | 0.9565 | 0.99374 | 8 500 |
| lgbm + lr_spline + logreg | 0.9567 | 0.99385 | 8 700 |
| catboost + lr_spline | 0.9572 | 0.99366 | 8 700 |
| **lr_spline (выбрана)** | **0.9591** | 0.99364 | **167** |

Конфигурация сплайнов не «удачная случайность» выбора по OOF — соседние
значения проверены тем же nested CV (`explore/nested_spline.py`) и дают
монотонно худший результат:

| n_knots / degree / C | nested F1 |
|---|---|
| **3 / 3 / 0.3 (выбрана)** | **0.9591** |
| 3 / 3 / 1.0 | 0.9583 |
| 3 / 3 / 0.1 | 0.9565 |
| 4 / 3 / 0.1 | 0.9569 |
| 4 / 3 / 0.3 | 0.9562 |
| 3 / 2 / 0.3 | 0.9559 |
| 5 / 3 / 0.3 | 0.9538 |
| 6 / 3 / 1.0 | 0.9513 |

10. **Производные признаки в финальной модели.** Пять отношений
    (`доход/цена телефона`, `долг/доход`, `остаток/доход`, `остаточная стоимость
    телефона`, `транзакции × доля онлайн`) дают +20 сплайновых колонок и
    +20 параметров. Проверено nested CV (`explore/derived_check.py`):
    без них F1 0.9581 / AUC 0.99374, с ними F1 0.9591 / AUC 0.99364 — то есть
    эффект в пределах ошибки (SE ≈ 0.0023). Признаки оставлены: по целевой
    метрике они не хуже, а интерпретируемая предметная связка полезна.

## Что сохраняется после обучения

`models/`:

* `lr_spline.joblib` — веса (26 КБ);
* `meta.json` — seed, порог, способ агрегации, метрики CV (общие и по каждой
  модели), полный список колонок признаков, коды категорий, встречавшиеся
  в обучении, версии Python и всех библиотек, дата и длительность обучения.

`predict.py` читает `meta.json`, сверяет список колонок с текущим и падает
при рассогласовании — это защита от тихого расхождения признаков между
обучением и инференсом.

## Самопроверка

`python verify.py` — 15 проверок, все проходят:

```
1. файлы весов на месте и непустые
2. веса загружаются, in-sample AUC = 0.9951
3. повторное обучение тем же seed даёт max|diff| = 0.00e+00
4. два запуска predict.py дают байт-в-байт одинаковый файл
5. колонки == [customer_id, accepted]; значения в {0,1}; пропусков нет;
   customer_id совпадает с sample_submission; доля единиц 0.3320 vs 0.3285
6. predict.py отрабатывает на батче из 1 и 3 строк; медианы в meta.json
   совпадают с медианами обучающей выборки
```

Пункт 6 — регрессия на реальный баг, найденный при разработке: если в батче
колонка целиком состоит из NaN (например, при вызове на одной строке, где
`insurance_claims` пуст с вероятностью 0.53), её медиана тоже NaN, и
`SplineTransformer` падал с `Input X contains NaN`. На полном наборе из 1000
строк полностью пустых колонок нет, поэтому на основной путь баг не влиял.
